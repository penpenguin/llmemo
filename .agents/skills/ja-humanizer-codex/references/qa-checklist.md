# 最終QAチェックリスト

改稿後、出力前にこのチェックを行います。ユーザーに見せる必要はありませんが、品質が不安な場合や依頼が「診断込み」の場合は要点を共有してもよいです。

## 1. 意味保存

- 数字、固有名詞、日時、金額、条件を変えていないか。
- 否定を肯定に、肯定を否定にしていないか。
- 「必ず」「可能性がある」「一部」「原則」などの強弱を変えていないか。
- 原因と結果の関係を勝手に強めていないか。
- 事実と意見の境界をぼかしていないか。
- 専門用語を言い換えて意味を落としていないか。

## 2. 追加情報の妥当性

- 実体験を勝手に足していないか。
- 顧客事例、数値、地域、期間、比較対象を捏造していないか。
- 「多くの人」「現場では」「よくある」など、根拠のない一般化をしていないか。
- 例を足した場合、それが仮例であることが分かるか。

## 3. 日本語の自然さ

- 語尾が連続していないか。
- 文長が均一すぎないか。
- 接続詞が多すぎないか。
- 名詞化が続いていないか。
- 「〜することができます」が残りすぎていないか。
- 「重要」「活用」「価値」「支援」「実現」などが連続していないか。

## 4. 構成

- 冒頭が一般論で長くなっていないか。
- 見出しや箇条書きが多すぎないか。
- 段落ごとの役割が重複していないか。
- まとめが予定調和になっていないか。
- 読者が次に何を考えるべきかが残っているか。

## 5. 媒体適合

- SNSなのに硬すぎないか。
- 技術記事なのに広告っぽくないか。
- LPなのに説明が長すぎないか。
- 顧客メールなのに砕けすぎていないか。
- 社内メモなのに丁寧すぎないか。
- 採用文なのに抽象的な美辞麗句だけになっていないか。

## 6. トーン

- 元の書き手よりも偉そうになっていないか。
- 謝罪文や依頼文で軽くなりすぎていないか。
- セールス文で煽りすぎていないか。
- カジュアル化しすぎて幼くなっていないか。
- 判断を入れた結果、元文より主張が強くなりすぎていないか。

## 7. 出力形式

- ユーザーが「本文のみ」と言ったのに解説を付けていないか。
- ユーザーが「差分」と言ったのに全文だけを出していないか。
- ユーザーが「診断」と言ったのに勝手に全面改稿していないか。
- 改稿文と調整点が混ざっていないか。
- コピペしやすい形になっているか。

## 危険な意味ズレ例

### 原文

```text
導入により、問い合わせ対応時間を削減できる可能性があります。
```

### NG改稿

```text
導入すれば、問い合わせ対応時間を確実に削減できます。
```

理由：可能性を確実な効果に変えている。

### OK改稿

```text
導入後は、問い合わせ対応にかかる時間を減らせる可能性があります。
```

## 強さ調整の目安

- 原文が「可能性があります」なら、根拠なしに「できます」にしない。
- 原文が「重要です」なら、文脈に応じて「先に見るべきです」「外せません」「差が出ます」へ調整できる。
- 原文が「期待されます」なら、「何が起きれば成功か」に置き換えると自然になる。
- 原文が「多くの」なら、根拠がなければ「少なくありません」「よく見かけます」程度に抑える。
