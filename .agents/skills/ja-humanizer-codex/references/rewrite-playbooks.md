# 改稿プレイブック

このファイルは、実際に文章を直すときの手順書です。元の意味を保ちながら、AI臭を消し、媒体に合う自然な日本語へ寄せます。

## 共通手順

### Step 1: 意味固定メモを作る

改稿前に、次を頭の中で固定します。ユーザーに出す必要はありません。

- 残す主張
- 残す数字、固有名詞、日時、条件
- 変えてはいけない専門用語
- 強めてはいけない表現
- 弱めてはいけない表現
- 追加してはいけない体験・実績・根拠

### Step 2: 余計な外骨格を外す

AI文は、最初に「全体像」を置き、次に「ポイント」を列挙し、最後に「まとめ」で閉じがちです。必要なら残しますが、読者が自然に読み進められる形へ直します。

削りやすいもの：

- 「この記事では〜について解説します」
- 「重要なのは以下の3点です」
- 「まず、〜。次に、〜。最後に、〜」
- 「このように、〜と言えるでしょう」
- 「今後ますます重要になります」

### Step 3: 抽象語を1段だけ下げる

無理な具体化はしません。根拠がないときは、抽象語を少しだけ読みやすくします。

例：

- 「価値を提供する」→「役に立つ形にする」
- 「ユーザー体験を向上させる」→「迷わず使えるようにする」
- 「業務効率化を実現する」→「手戻りや確認待ちを減らす」
- 「多様なニーズに対応する」→「使い方の違いに合わせられる」

### Step 4: 語尾と文長を整える

語尾は散らします。ただし、不自然な体言止めや口語を入れすぎないでください。

使えるパターン：

- 短い断定：「ここが一番大きい。」
- 補足：「ただ、万能ではない。」
- 軽い問い：「では、どこを見るべきか。」
- 体言止め：「最初に見るのは、導入後の手戻り。」
- 少しくだけた言い換え：「要するに、迷う時間を減らす設計です。」

### Step 5: 書き手の判断を入れる

書き手の判断は、元の文に含まれる価値判断から引き出します。勝手に思想や感情を追加しません。

使える判断軸：

- 優先順位：「まず見るべきなのは〜」
- 注意点：「ただし、ここは誤解されやすい」
- 限界：「ここだけでは判断できない」
- 見立て：「現時点では〜と見るのが自然」
- 読者への接続：「実務で困るのは〜」

### Step 6: 結論を作り直す

締めは、一般論よりも読者の判断や次の行動に寄せます。

弱い締め：

- 「今後の展開が注目されます」
- 「ますます重要になるでしょう」
- 「適切に活用することが求められます」

強い締め：

- 「迷ったら、まずは導入コストより運用後の手戻りを見たほうがいい。」
- 「派手な機能より、毎日使う人が詰まらない設計かどうかが差になります。」
- 「結局、比較すべきなのは機能数ではなく、現場で続くかどうかです。」

## モード別プレイブック

### rewrite: 全面改稿

使う場面：ブログ、note、LP、SNS、採用文など、自然さと説得力が重要な文章。

手順：

1. 主張を保ったまま、段落順を必要に応じて変える。
2. 導入の一般論を削り、読者の関心に近い一文から始める。
3. 抽象語を具体的な行為・判断・場面へ置き換える。
4. 予定調和な結論を作り直す。
5. 最後に元文と照合し、意味ズレを直す。

出力例：

```text
以下、自然な日本語に寄せて直しました。

（改稿文）

主な調整点:
- 冒頭の一般論を削り、読者の関心に近い入りに変更
- 「活用」「価値」などの抽象語を具体的な行為へ置換
- 結論を予定調和な表現から、判断基準が残る締めに変更
```

### detect: 診断のみ

使う場面：ユーザーが先に問題点を知りたいとき。

手順：

1. AI臭スコアを出す。
2. 主因を3つまで挙げる。
3. 代表的な箇所を引用し、理由を説明する。
4. 一部だけAfterを示す。
5. 全面改稿は求められない限り行わない。

### edit-in-place: 最小編集

使う場面：原稿の構成を崩せないとき。契約文、FAQ、仕様書、承認済み記事、既存LPなど。

手順：

1. 段落順は維持する。
2. 文ごとの意味を変えず、語尾・接続・冗長表現だけ直す。
3. 数字、条件、免責、専門用語を保つ。
4. 自然化のための大胆な補足は避ける。

### compress: 圧縮

使う場面：メール、Slack、社内メモ、PRコメント、開発者向け説明。

削るもの：

- 「ご確認いただけますと幸いです」→「ご確認ください」または「確認お願いします」
- 「〜についてご説明させていただきます」→「〜を説明します」
- 「可能性があると考えられます」→「可能性があります」または「ありそうです」
- 「〜することができます」→「〜できます」または「〜できます」を動詞化
- 「〜において」→「〜で」

ただし、謝罪・依頼・顧客対応では、礼儀を削りすぎないこと。

### style-transfer: 文体寄せ

使う場面：ユーザーが「もっと○○っぽく」と指定したとき。

守ること：

- 指定文体を真似るのはリズム、語彙、温度、情報密度まで。事実は増やさない。
- 著名人や存命人物の文体模倣を求められた場合は、固有の癖をそのまま再現せず、一般的な特徴に抽象化する。
- ブランド文体の場合は、ユーザーが提示したガイドラインを優先する。

## 媒体別の直し方

### note・ブログ

- 冒頭は一般論より、違和感、発見、問い、具体的な場面から入る。
- 語尾は少し揺らしてよい。
- 書き手の見立てを入れる。
- まとめは短く、余韻か次の問いで閉じる。

### X・Threads・短文SNS

- 一文目で読者の関心に刺す。
- 箇条書きは短く。
- 「ですます」より、少し言い切りを増やす。
- きれいにまとめすぎない。

### LP・広告

- 抽象的な価値より、読者の困りごとと行動変化を書く。
- 機能説明はベネフィットに接続する。
- 煽りすぎない。具体性がない誇張は削る。
- CTA前の文章は短く。

### 採用・コーポレート

- 「成長環境」「裁量」「挑戦」だけでは弱い。どんな仕事、どんな意思決定、どんな難しさがあるかを書く。
- 会社の良さだけでなく、向いている人・向いていない人の輪郭を出す。
- 過度にカジュアルにしない。

### 技術記事

- 広告語を減らし、条件、制約、トレードオフを書く。
- 「簡単にできます」は危険。前提条件を書く。
- 手順は箇条書きでよいが、説明文の抽象語を減らす。
- 読者が詰まりやすいポイントを先に出す。

### メール

- 件名、依頼、期限、相手にしてほしいことを明確にする。
- 過剰な前置きは削る。
- 相手が顧客・上位者・初対面なら丁寧さを残す。
- 社内なら短くする。

## 置換ではなく判断する

次の置換は便利ですが、必ず文脈で判断してください。

- 「重要です」→「先に見たほうがいい」「ここで差が出る」「外せない」
- 「可能性があります」→「ありそうです」「起こり得ます」「まだ断定できません」
- 「活用する」→「使う」「組み込む」「現場に入れる」「判断材料にする」
- 「支援する」→「手伝う」「負担を減らす」「進めやすくする」
- 「実現する」→「できるようにする」「形にする」「届くようにする」
- 「最適化する」→「無駄を減らす」「条件に合わせる」「詰まりを減らす」
