# 文体プリセット

依頼に文体指定がない場合は「標準：自然なビジネス日本語」を使います。媒体、読者、目的が分かる場合は、該当プリセットを調整してください。

## 標準：自然なビジネス日本語

### 向いている用途

記事、提案文、社内外向け説明、メール、プロフィール、サービス紹介。

### 方針

- 丁寧だが、過剰にかしこまらない。
- 「です・ます」を基本にしつつ、語尾を少し散らす。
- 抽象語を減らし、判断や具体性を足す。
- 読者の負担を減らすため、前置きを短くする。

### 避けること

- 砕けすぎ。
- 「〜と言えるでしょう」の多用。
- きれいなだけの結論。

## カジュアル：note・個人ブログ・SNS

### 向いている用途

note、X、Threads、個人ブログ、コミュニティ投稿。

### 方針

- 一文目で違和感、発見、問いを出す。
- 体温のある言い切りを少し増やす。
- 「ですます」だけにしない。
- 余白や間を残す。

### 例

```text
Before: AIを活用することで、文章作成の効率化が期待できます。
After: AIを使うと、文章を書く速度はたしかに上がります。ただ、そのまま出すと「速いけど薄い」文章になりやすい。
```

## 端的：Slack・社内メモ・PRコメント

### 向いている用途

Slack、Teams、GitHub PR、Issue、社内メモ、作業依頼。

### 方針

- 用件、判断、次のアクションを先に出す。
- 敬語と前置きを減らす。
- 箇条書きは使ってよい。
- 説明より実行しやすさを優先する。

### 例

```text
Before: お忙しいところ恐れ入りますが、こちらの内容についてご確認いただけますと幸いです。
After: こちら確認お願いします。今日中に見られると助かります。
```

## 信頼：採用・コーポレート・広報

### 向いている用途

採用ページ、会社紹介、代表メッセージ、プレスリリース、IRに近い文書。

### 方針

- 誇張を避ける。
- 会社の考え方、意思決定、現場の実態を出す。
- 丁寧さは保つが、抽象語を並べない。
- 実績や数字は正確に扱う。

### 例

```text
Before: 私たちは挑戦を続ける仲間を求めています。
After: まだ整っていない部分も多い会社です。だからこそ、自分で課題を見つけて動ける人には任せられる余地があります。
```

## 技術：開発者向け記事・仕様説明

### 向いている用途

技術ブログ、README、設計メモ、仕様書、エンジニア向け記事。

### 方針

- 結論、前提、制約、手順を明確にする。
- 広告語を減らす。
- 「簡単」「シームレス」などの主観語には条件を付ける。
- 読者が詰まりそうな箇所を先に示す。

### 例

```text
Before: このAPIを使うことで、柔軟なデータ連携を簡単に実現できます。
After: このAPIを使うと、外部サービスから注文データを取得できます。実装で詰まりやすいのは、取得処理そのものより認証とリトライ設計です。
```

## セールス：LP・広告・商品説明

### 向いている用途

LP、広告文、商品説明、営業資料、サービスサイト。

### 方針

- 読者の困りごとから入る。
- 機能ではなく、行動や判断の変化を書く。
- 誇張より具体性。
- CTA前は短く、迷いを減らす。

### 例

```text
Before: 貴社のマーケティング活動を次のステージへ導きます。
After: 広告を増やす前に、どこで見込み客が離れているのかを見直します。
```

## 丁寧：顧客メール・お知らせ

### 向いている用途

顧客メール、謝罪文、案内文、問い合わせ返信、重要なお知らせ。

### 方針

- 丁寧さは残す。
- 前置きは短くする。
- 何が起きたか、相手に何をしてほしいか、期限があるかを明確にする。
- 謝罪文では言い訳っぽい抽象語を避ける。

### 例

```text
Before: この度はご不便をおかけしてしまい、誠に申し訳ございません。
After: この度はご不便をおかけし、申し訳ございません。現在、原因を確認しており、本日18時までに次の対応をご連絡します。
```

## 硬め：行政・研究・白書寄り

### 向いている用途

調査報告、研究紹介、行政資料、白書、制度説明。

### 方針

- 砕けさせない。
- 定義と条件を明確にする。
- 「重要です」だけで終わらせず、対象範囲や未確定部分を書く。
- 冗長な言い換えは削る。

### 例

```text
Before: 今後の制度設計において重要な論点になると考えられます。
After: 制度設計では、対象範囲と運用コストを分けて検討する必要があります。特に、現場側の確認負荷は早い段階で見積もるべきです。
```

## 文体選択の簡易ルール

- 読者が忙しい社内メンバーなら「端的」
- 読者が顧客なら「丁寧」か「標準」
- 読者がエンジニアなら「技術」
- 読者が求職者なら「信頼」
- 読者がSNSのフォロワーなら「カジュアル」
- 読者が購入検討者なら「セールス」
